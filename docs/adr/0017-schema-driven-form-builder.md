# ADR-0017: Schema-driven spec form builder and Studio's first write path

## Status

Accepted

## Context

Phase 14 turns Studio from a read-only viewer (Phase 13) into an editor: forms generated from the real Zod schema for each resource type, a field-level edit expressed as a structured patch, and — for the first time anywhere in Studio — a real write back to `agentform.yaml`. The core principle from §34 still governs: the specification file is the single source of truth, and no edit reaches disk without passing through the exact same schema → semantic/IR → policy pipeline the CLI already enforces.

## Decision

- **Forms are generated from real per-resource Zod schemas via `z.toJSONSchema`, not a hand-maintained form-field table.** `generateResourceFormSchema('models' | 'tools' | 'agents' | 'workflows')` (`packages/studio-core/src/form-schema.ts`) calls `z.toJSONSchema` directly on `modelSchema`/`toolSchema`/`agentSchema`/`workflowSchema` — the exact same schemas `@agentform/schema` validates against — so the form can never drift from what the server actually accepts.
- **`tools` is a real `z.discriminatedUnion('type', [...])`, not a flat object — found by a failing test, not assumed.** Its JSON Schema is a top-level `oneOf`, structurally different from the other three resource types. `ResourceForm` (studio-web) handles only one concrete object shape at a time; `ResourceEditor` resolves _which_ shape — via a variant picker keyed on the real `type` discriminator — before `ResourceForm` ever sees a schema. This is recorded as a real, if minor, generalization the form-schema design needed, not special-cased away.
- **The generic form renderer handles the common JSON Schema field kinds (string, enum, number/integer, boolean, string array, nested object with fixed properties) and falls back to a raw JSON field for everything else** — a free-form record (`additionalProperties`, no fixed `properties`, e.g. an agent's `inputSchema`/`metadata`), an array of objects, or a schema with no plain `type`. This is the same "faithful where unambiguous, honest fallback where not" discipline the compiler's own adapters already follow for constructs they can't safely translate — a raw-JSON field a user can still edit correctly beats a form silently dropping or mis-rendering a field it doesn't understand.
- **The write path (`POST /api/spec/patch`) never trusts the incoming patch as pre-validated.** `applySpecPatch` (`apps/studio-server/src/lib/apply-spec-patch.ts`) re-reads the project fresh from disk on every call, applies the patch to a plain in-memory value, and re-runs the complete pipeline — schema validation, semantic/IR validation, and policy evaluation (`BUILTIN_POLICIES` at the project's real configured severities) — before anything touches a file. Any error-severity diagnostic at any stage rejects the write outright and returns the diagnostics; nothing partial is ever persisted.
- **The actual file write targets a real parsed `yaml.Document`, not a re-serialized plain object.** `Document#setIn`/`deleteIn` (the real, installed `yaml` package's own API, verified empirically before this was built) mutate only the node a patch operation targets — comments, key order, and formatting everywhere else in the file survive untouched. This is the literal mechanism behind "lossless `spec → form → spec` round trip," not just a description of the goal.
- **Only single-file projects can be written back.** A project's real `sourceMap` (from `loadProject`) records which file each field actually came from; if a patch's target project references more than one distinct file (auto-discovered `agents/`/`tools/`/`workflows/` directories, or a `$ref`), the write is refused with an honest `AGF8001` diagnostic rather than guessing which file a field belongs in. Multi-file write support is a real, deferred gap, not a silent limitation.
- **`loadPolicyConfig` and `policyResultsToDiagnostics` moved from the CLI into `@agentform/policy`.** Both had zero CLI-specific dependencies; `studio-server`'s write path needed the exact same policy-config loading and result-to-diagnostic conversion every CLI command already had, so this is a pure move (behavior, filename convention, and every existing CLI call site's semantics are unchanged), not a new implementation living in two places.
- **A patch is one `add`/`replace` operation targeting the whole resource object (`['spec', resourceType, resourceId]`), not a granular per-field diff.** `SpecPatchOperation`'s `value` can be any JSON value, so replacing an entire resource in one operation is simple, correct, and sufficient for what a form actually needs to express — a field-level diffing algorithm would be real complexity with no present payoff, since the server re-validates the _result_ regardless of how coarsely or finely the patch that produced it was expressed.

## Alternatives considered

- **Hand-maintained form field definitions per resource type**: rejected — the schema and the form would inevitably drift the first time either changed without the other; generating from the real Zod schema makes drift structurally impossible.
- **Field-level patch diffing** (comparing old vs. new resource object and emitting one operation per changed field): rejected as unnecessary complexity — a single whole-resource `replace`/`add` is simpler, and the server-side re-validation is identical either way.
- **Extending `@agentform/parser`'s `loadDocument` to also return the real `yaml.Document`**: considered, then rejected — `apply-spec-patch.ts` parses the entry file's own text a second time, directly, only for the write step; `loadProject` (unmodified) still owns the full resolved-value read path used for validation. This keeps `@agentform/parser`'s existing read-only contract exactly as Phase 13 (ADR-0016) established it, at the cost of one extra (cheap) parse.
- **Best-effort multi-file writes** (writing to whichever file a source-map entry says a field came from): rejected for this phase — correctly handling a patch that touches fields split across files, or that adds a field with no existing file to belong to, is real, unsolved design work; refusing clearly is safer than a plausible-looking write that silently corrupts a `$ref`ed file's own structure.

## Consequences

- `packages/studio-core` gains `form-schema.ts`, and `patch.ts`'s `applyPatch` is now generic (`<T>(document: T, patch: SpecPatch): T`) rather than `AgenticApplication`-specific, since the server needs to patch a raw, not-yet-validated value before knowing whether it's even valid.
- `apps/studio-server` gains its first dependencies on `@agentform/policy`, `@agentform/diagnostics`, and the `yaml` package directly, and its first diagnostic code range (`AGF8xxx`, `apps/studio-server/src/lib/codes.ts`).
- `apps/cli/src/lib/policy-output.ts` now holds only CLI-specific human-readable summary formatting (`PolicySummary`, `summarizePolicyResults`, `formatPolicySummary`); every CLI command that used `loadPolicyConfig`/`policyResultsToDiagnostics` now imports them from `@agentform/policy` instead, with no behavior change.
- Real, reusable double for write-path tests: since `@agentform/parser`'s `createInMemoryFileSystem` closes over an immutable snapshot (a deliberate design choice — the parser itself never writes), the write-then-re-read-from-disk step this phase's tests need to observe required a small test-only shared mutable filesystem+writer double, not `@agentform/parser` changes.

## Security impact

This is Studio's first write path, and the one this repo's threat model (ADR-0016's "Studio local server exposure" entry) explicitly flagged as needing its own accounting. The design intent recorded there — re-run the full validate → IR → policy pipeline server-side, never trust a browser-submitted patch as pre-validated — is exactly what `applySpecPatch` does; `docs/security/threat-model.md` gains a dedicated write-path entry recording this as implemented, not just intended. No new secret-handling surface: a patch can supply an `${env.*}` reference exactly like hand-authored YAML can, but cannot supply an inline secret any more successfully than typing one directly into the file could — the same policy checks (`AF001` et al.) apply to a patched document as to any other.

## Migration impact

Additive to Studio; the CLI's `loadPolicyConfig`/`policyResultsToDiagnostics` relocation is a pure move with no behavior change for any existing command. No generated artifact, specification file, or CLI command's user-visible behavior changes.
