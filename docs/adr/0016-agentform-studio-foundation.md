# ADR-0016: Agentform Studio foundation — architecture and Phase 13 scope

## Status

Accepted

## Context

§34 of the master spec introduces "Agentform Studio," a web application layered on top of the stable 12-phase core (plus the post-v1 Agno adapter) — a second, visual interface onto the same `agentform.yaml` spec the CLI already reads, edits, and compiles. Its own stated core principle: the specification remains the single source of truth; Studio is a view and an editor over the IR, never a parallel authority. The spec gates this work on "the core (Phase 12) is stable," which it is, and lays out a 6-phase arc (13–18) delivered with the same branch/PR/commit discipline as the original 12.

This is a structurally different commitment than anything shipped so far: it introduces the repo's first frontend (`apps/studio-web`), first long-running HTTP server (`apps/studio-server`), and first browser-facing surface. None of the 12 merged phases established any precedent for these — every decision below had to be made from first principles against this specific repo's existing conventions, not inherited from an existing pattern.

Phase 13 ("Studio foundation and spec I/O") is scoped narrowly and deliberately: `apps/studio-web` + `apps/studio-server` skeletons, `packages/studio-core`'s shared model and patch engine, loading/validating/displaying an existing spec read-only, and live diagnostics in the UI. No editing, no canvas, no GenAI — those are Phases 14–18.

## Decision

- **Frontend: Vite + React.** React is named explicitly by the spec. Vite was chosen over Next.js because Next's SSR/routing/edge machinery serves no purpose for a localhost companion GUI and would either force merging `studio-web`/`studio-server` into one process (contradicting the spec's explicit app split, which matters for keeping the future GenAI-orchestration boundary server-only) or run two overlapping servers. Vite also shares its transform engine with Vitest, already this repo's only test runner, so `studio-web` needs one config file for dev/build/test, not three.
- **Backend: Fastify.** The first HTTP server in the repo, so no existing pattern to match — this optimizes for the repo's demonstrated bias toward mature, widely-adopted, natively-TypeScript tooling (`commander`, `pino`, `zod` used everywhere already). `fastify-type-provider-zod` gives typed request/response derived directly from Zod schemas, the strongest possible alignment with "Zod is already the schema tool of choice everywhere." Express was rejected — schema validation there is bolted on, not integrated, and its TypeScript story is `@types/express`, not native. Hono was rejected — it's edge-runtime-first (Cloudflare Workers/Deno), a mismatch for a plain local Node process.
- **API: plain typed REST, not tRPC or GraphQL.** DTOs (`AgenticApplication`, `Diagnostic`, `SpecDocumentResponse`, `HealthResponse`) live in `packages/studio-core` and are reused verbatim by both apps — no forked types. tRPC would couple the client directly to the server's router types, cutting against the clean, auditable client/server boundary Phase 17's GenAI orchestration needs (server-only, browser never touches a model provider). GraphQL is disproportionate to two read-only `GET` endpoints.
- **`studio-server` dev loop: `tsx watch`, not Node's `--experimental-strip-types` or `nodemon`+`ts-node`.** The repo's Node floor (`>=22.0.0`) isn't pinned to a late-enough minor to rely on an experimental flag, and this repo never reaches for experimental flags elsewhere. `tsx` is a single, mature, esbuild-backed dependency doing the same job `nodemon`+`ts-node` would need two packages for; it does no type-checking during dev, which isn't a regression — `typecheck` is already always a separate script from `build`/`dev` everywhere else in this repo.
- **Frontend tests: Vitest + `@testing-library/react` + jsdom, not happy-dom.** jsdom is Testing Library's own documented default and the more spec-complete DOM implementation; happy-dom's main edge is raw speed at large suite sizes, which doesn't matter yet at Phase 13's scale.
- **Deployment: local-only, single-user, no auth — the `prisma studio`/`drizzle-kit studio` model, not a hosted multi-tenant service.** Nothing in any of the 12 merged phases has a user/tenant concept anywhere (schema, IR, state backends are all single-project), and the spec's own language — "a second interface into the same single source of truth" — never mentions users or tenants. `studio-server` binds to `127.0.0.1` only, serves exactly one project directory per process via `AGENTFORM_STUDIO_ROOT` (mirroring the CLI's own `--cwd`), and applies a narrow CORS allowlist (the Vite dev origin only, not a wildcard) as cheap defense-in-depth against an arbitrary webpage in the same browser reaching a no-auth local service — not itself an authentication mechanism, and not a contradiction of "no auth."
- **`packages/studio-core` ships with only `@agentform/schema` + `@agentform/diagnostics` + `@agentform/ir` + `zod` as dependencies for Phase 13**, not the full `schema`/`ir`/`planner`/`policy` set the architecture section (§34.3) names for the package's eventual scope. Nothing in Phase 13's code imports `planner` or `policy` — its diagnostics come from the parse → schema → semantic/IR pipeline only (`buildSpecDocument` wraps `@agentform/ir`'s `buildIR` directly), never a policy check. Adding unused `workspace:*` dependencies now would misrepresent actual usage and add a real (if small) Turborepo build-graph edge with no payoff. `planner`/`policy` get added the moment a later phase's code actually imports them — most likely Phase 14 (patch re-validation) or a plan-preview surface.
- **`GET /api/spec` is one atomic snapshot, not split into a separate diagnostics endpoint.** Splitting would mean two independent re-reads of a project directory that could be mid-edit between the two requests, risking an inconsistent application/diagnostics pairing in the UI for no benefit. Both `/api/health` and `/api/spec` always return `200` — an invalid spec is a successful response carrying error-severity diagnostics as data, not a transport failure, so the frontend branches on response shape rather than HTTP status.
- **No `@agentform/registry` module resolution in `studio-server`'s load path.** No existing example project uses `spec.modules`, so there's nothing to exercise it against yet, and it would pull in signing/trust complexity Phase 13 doesn't need. Added the moment that changes.
- **No IR/workflow-graph exposure over HTTP yet.** `buildSpecDocument` deliberately discards `buildIR`'s Map-keyed `ir` result — not JSON-safe as-is, and Phase 13's own scope is "display the spec" and "diagnostics," not the graph. `@agentform/core`'s `flattenMaps` (already used by the CLI's own `toPlainObject`, per the Phase 11 apply-command work) is the established, ready-to-reuse mechanism for when Phase 15's canvas actually needs the workflow graph.

## Alternatives considered

- **Next.js for `studio-web`**: rejected — see Decision above; its value proposition doesn't apply to a localhost dev-tool GUI.
- **tRPC for the client/server boundary**: rejected — couples client and server types together in a way that fights the server-only GenAI boundary Phase 17 needs, and would be the first RPC/codegen paradigm in a monorepo whose entire texture is deliberately mainstream and unsurprising.
- **A Fastify decorator (`app.decorate('config', ...)`) for threading `rootDir`/`fs` into route handlers**: considered, then rejected in favor of passing them as plain function parameters to each `registerXRoute(app, options)` call — simpler, more directly testable per-route, and avoids TypeScript module-augmentation ceremony for what is currently two routes.
- **Hosted multi-tenant deployment with real auth**: rejected outright per the Decision above — no existing part of this codebase has a user/tenant concept, and inventing one for Studio alone, unprompted, would be a significant, undiscussed scope expansion the spec itself gives no indication of wanting.

## Consequences

- Three new workspace members (`packages/studio-core`, `apps/studio-server`, `apps/studio-web`) join the `pnpm-workspace.yaml` `apps/*`/`packages/*` globs automatically — no workspace config changes needed.
- `apps/studio-web` is the first package in the repo using TypeScript project references (a solution `tsconfig.json` referencing `tsconfig.app.json`/`tsconfig.node.json`), because the browser app (`Bundler` resolution, DOM libs, `jsx`) and the Node-run `vite.config.ts` (this repo's usual `NodeNext`) genuinely need different compiler settings — no other package in the repo needs this split. `*.tsbuildinfo` is now repo-wide gitignored as a result.
- `eslint.config.js` gained one additional block scoped to `apps/studio-web/**/*.{ts,tsx}` (React Hooks rules, `react-refresh`'s `only-export-components`) — zero change to lint behavior anywhere else in the monorepo.
- `turbo.json` gained a `dev` task (`persistent: true`, uncached, `dependsOn: ["^build"]`) — the first non-one-shot task in the pipeline. It naturally scopes to just `studio-web`/`studio-server`, the only two packages that declare a `dev` script.
- Every response type crossing the `studio-server` ↔ `studio-web` boundary is declared once, in `studio-core`, and reused by both sides — there is no independent frontend type for "what a spec looks like."

## Security impact

New network-facing surface in this repo for the first time: `studio-server` listens on `127.0.0.1` only, with no authentication, by design (see Decision). This is safe under the "single local developer, single local project" threat model the whole CLI already operates under — the same person who could already read/edit `agentform.yaml` directly on disk can now also read it over HTTP on their own machine. The narrow CORS allowlist is the one new mitigation, addressing a real (if lower-severity) local threat: an arbitrary malicious webpage open in the same browser attempting to read the developer's spec via an unauthenticated `fetch('http://localhost:4310/api/spec')`. Phase 13 ships no write endpoint, so there is no injection or trust-boundary risk yet from a browser-submitted payload; `docs/security/threat-model.md` is updated with an explicit flag that Phase 14's write path must re-run the full schema → semantic → IR → policy pipeline server-side before ever touching a file, never trusting a browser-submitted patch directly.

## Migration impact

Purely additive. No existing package, CLI command, generated artifact, or specification file changes behavior. `agentform` the CLI is entirely unaware Studio exists.
