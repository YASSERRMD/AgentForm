# ADR-0022: Studio access control and audit integrity

## Status

Accepted

## Context

The Agentform Studio arc (Phases 13-18, ADR-0016 through ADR-0021) closed with a deliberate, explicitly-documented "no authentication by design" decision, repeated near-verbatim across five threat-model sections: Studio is a single-developer local tool, the same trust model `prisma studio`/`drizzle-kit studio` already operate under — whoever can run `studio-server` on their machine could already read `agentform.yaml` directly from disk, so an unauthenticated local HTTP view of the same file changes nothing about who can see it.

That reasoning holds only when the port and the file are reachable by the same party on the same machine. It silently stops holding the moment Studio is reached over port-forwarding, from inside a devcontainer, or from a codespace — increasingly common ways to run a "local dev tool" today, where the person opening the forwarded port in a browser is not necessarily the same person (or the only person) with filesystem access to the project. This is a real, if narrow, gap in an otherwise-sound threat model, not a reason to reverse Studio's local-first identity.

Separately, `.agentform/studio-audit.jsonl` (Phase 18, ADR-0021) was explicitly documented as _not_ a security control, unlike `.afplan` (`@agentform/planner`) and `.agentform/test-results.json` (`@agentform/evaluator`), which both are. An append-only, ever-growing log has a different tampering surface than either of those one-shot documents: a single content hash proves a _document_ wasn't altered, but says nothing about whether a _line_ was deleted, reordered, or truncated from a log that's supposed to keep growing.

Both gaps close in the same pass because they touch the same subsystem (`apps/studio-server`) and ship together; this ADR covers both rather than splitting into two documents describing one coordinated hardening effort.

## Decision

### Audit log: hash-chained, not just per-entry hashed

Each `AuditEntry` gains `previousEntryHash`/`entryHash`. `entryHash` (`computeContentHash`, the same canonicalization `.afplan`/`test-results.json` already use, from `@agentform/ir`) covers every other field on the entry _including the previous entry's own hash_ — a chain, not independent per-entry hashes. Independent hashing would only prove a single line wasn't edited after being written; chaining also detects deletion, reordering, and truncation across the log's history, which is the actual gap an ever-growing append-only log has that a one-shot document's hash doesn't. `previousEntryHash` is either the prior line's `entryHash`, or the literal string `'genesis'` (never `sha256:`-prefixed, so it can't be confused with a real hash) for the first entry.

`appendAuditEntry` only reads the last existing line's hash — it never re-verifies the whole chain on every write, keeping appends cheap. A new `verifyAuditLog` is the explicit, separate read-side check, run on every `GET /api/audit`; a pre-hardening legacy line with no hash fields at all is treated as unverifiable rather than a false tamper report, and the running chain expectation resets to `'genesis'` for whatever follows it, so real tampering later in the file is still caught. **Verification never gates a write** — this is downstream observability about writes that already succeeded, not a precondition for a future one, the same as `.afplan`'s own honest limit of detecting rather than preventing a direct file edit. `readAuditLog` also normalizes a legacy entry's missing hash fields to a `'legacy'` placeholder before it reaches the HTTP response schema — found as a real bug during this pass's own live verification (see Consequences below), not designed in from the start.

`@agentform/ir`'s `computeContentHash` is now a direct dependency of `studio-server`, not `@agentform/planner`'s higher-level `verifyPlanFile` (which would wrongly pull in `@agentform/state`) — the same convention `packages/evaluator/src/results-record.ts` already established for `test-results.json`: depend on the low-level primitive directly and reimplement the small wrapper locally, rather than share a high-level verify function cross-package.

### Opt-in bearer-token auth, not a reversal of "no auth by design"

`AGENTFORM_STUDIO_TOKEN` is unset by default — Studio's zero-config path is completely unchanged. When set, a new `onRequest` hook (`lib/auth.ts`) requires a matching bearer token on **every** route, including `GET /api/health` (which otherwise leaks `rootDir`, an absolute filesystem path) — no per-route exemption, since "the token gates the whole port, no exceptions to remember" is a simpler, more honest story than a partial allowlist.

`Authorization: Bearer <token>` is the mechanism for every ongoing request. `?token=<token>` is accepted only as a bootstrap fallback for a browser's first navigation (Studio's own startup log prints a ready-to-open URL carrying it, mirroring Jupyter's `--NotebookApp.token` banner) — never relied on beyond that first load, since Fastify's `logger: true` logs request URLs including query strings, and a token present in every request's URL would leak into the server's own log output. `apps/studio-web`'s new `auth-token.ts` reads the query param once at startup, stores it in `sessionStorage`, and strips it from the visible URL via `history.replaceState` so it never lingers in browser history; a plain refresh falls back to the stored value.

Token comparison uses `node:crypto`'s `timingSafeEqual`, with an explicit length-equality guard first — `timingSafeEqual` throws on a length mismatch rather than returning `false`, and an early, variable-cost throw before the constant-time comparison would itself leak exactly what a naive `===` does.

**The auth hook is registered after `@fastify/cors`, not before — this ordering is load-bearing, verified directly against the installed `@fastify/cors@11.3.0` source, not assumed from generic Fastify knowledge.** `@fastify/cors`'s own code comment states the exact requirement: _"The preflight reply must occur in the hook. This allows fastify-cors to reply to preflight requests BEFORE possible authentication plugins."_ Fastify runs same-type hooks in registration order; a CORS preflight (`OPTIONS`, carries no `Authorization` header by browser design) is fully resolved by CORS's own earlier-registered hook and never reaches the auth hook, while a real GET/POST/PUT passes through both in order. Reversing this order would break every cross-origin request the moment a token is configured. This is proven by a dedicated regression test (`apps/studio-server/src/app.test.ts`), not left to code-review trust alone — the plan for this pass called that test out explicitly as "the one this whole mechanism's correctness actually depends on."

### Rate limiting, scoped to the 4 GenAI/chat routes only

`@fastify/rate-limit` is registered with `global: false` — registering the plugin doesn't limit anything by itself; only `POST /api/genai/prompt-to-spec`, `/prompt-to-design`, `/chat/spec`, `/chat/design` opt in via `config: { rateLimit: GENAI_RATE_LIMIT }`, each with its own independent bucket. `GENAI_RATE_LIMIT = { max: 20, timeWindow: '1 minute' }` — comfortably above realistic interactive use (read a proposal, tweak, resubmit — roughly one request per 3s sustained) while bounding a runaway client from placing unbounded real-dollar load on whatever provider is configured. Gated behind a new optional `genaiRateLimit` `BuildAppOptions` field (omit → disabled), mirroring the exact `devOrigin`/`authToken` convention — every existing `genai.test.ts`/`chat.test.ts` call to `buildApp({...})` omits it, so no existing test's behavior changes.

### Explicit field/body bounds

`.max()` bounds were added to every field in `studio-core`'s and `studio-design`'s `http-contracts.ts` that had `.min(1)` (or no bound at all) but no upper bound: `prompt`/`message` (4000 chars), `chatHistoryMessageSchema.content` (4000 chars, previously entirely unbounded), `history` arrays (50 entries), `patch` arrays (200 operations), `specPatchOperationSchema.path` (20 segments, already had `.min(1)`). `specPatchOperationSchema.value` stays deliberately unbounded — legitimate variable-size content (a whole resource value) — with Fastify's `bodyLimit` (now made explicit at `1_048_576` bytes, matching v5's own implicit default) as the right backstop for that field instead.

## Alternatives considered

- **mTLS, a firewall rule, or "just don't port-forward it"**: rejected as disproportionate to what this tool is and as advice that doesn't survive contact with how people actually use devcontainers/codespaces today — an opt-in shared-secret token is a much lower-friction control that directly addresses the gap this ADR opened with.
- **Session cookies / a login flow**: rejected — Studio has no user accounts and no multi-tenant concept (see ADR-0016's own "hosted multi-tenant: rejected outright" reasoning); a single shared bearer token matches the single-developer trust model exactly, without inventing session lifecycle machinery this tool has no other use for.
- **Full OAuth / SSO**: rejected for the same reason, at even greater disproportion — there is no identity provider to federate with and no multi-user concept for OAuth's scopes/consent model to protect.
- **A global rate limit on the whole app**: considered and rejected — every non-GenAI route is a local filesystem read/write with no outbound cost; rate-limiting them protects nothing a GenAI-scoped limit doesn't already cover, and would only add friction to the canvas/form-editing UI's own normal request volume.
- **Independent per-entry audit hashes (no chaining)**: considered, since it's simpler. Rejected — it only proves a single line wasn't edited after being written; it can't detect a deleted, reordered, or truncated entry, which is the actual gap an ever-growing append-only log has relative to `.afplan`'s one-shot-document hash.

## Consequences

- New `apps/studio-server/src/lib/auth.ts` (`extractBearerToken`, `tokensMatch`, `createAuthHook`), `lib/rate-limit-config.ts` (`GENAI_RATE_LIMIT`). `BuildAppOptions` gains `authToken?`/`genaiRateLimit?`, both optional and both defaulting to today's exact behavior when omitted.
- `config.ts` gains `authToken` parsing (trimmed, blank/whitespace treated as unset, a short token warns but never throws) and, per an explicit decision confirmed before implementation, **fail-loud validation**: an invalid `AGENTFORM_STUDIO_PORT` (not an integer in `[1, 65535]`) or an unrecognized non-empty `AGENTFORM_STUDIO_GENAI_PROVIDER` value now throws `StudioConfigError` at startup rather than silently falling back to a default — reversing the one existing test that asserted the old silent-fallback behavior, which was rewritten rather than extended. This matches this codebase's dominant "fail loud, never silently guess" convention elsewhere (e.g. `agentform`'s own CLI argument validation) more closely than the previous behavior did.
- **A genuine implementation bug found and fixed during this pass, not merely a design detail**: `@fastify/rate-limit` captures each route's `config.rateLimit` via its own `onRoute` hook, which only applies to routes registered _after_ that hook has actually finished installing — not merely after `register()` is _called_. A route added immediately afterward, in the same synchronous tick `buildApp` runs in, was silently never rate-limited at all — confirmed empirically with a minimal isolated reproduction, not assumed from the plugin's documentation. Fixed by wrapping the GenAI/chat route registrations in `app.after(() => { ... })`, which defers them until every plugin queued so far (rate-limit included) has finished loading, while keeping `buildApp` itself fully synchronous — no caller needed to change. This is exercised by the _entire_ existing test suite, not just the two new rate-limit tests, since the wrapping is unconditional.
- **A second genuine bug found only by live-testing against real, pre-existing audit data, not synthetic test fixtures**: a legacy audit entry (written before this pass, with no hash-chain fields on disk) failed the now-required response schema and 500'd the entire `GET /api/audit` endpoint via `fastify-type-provider-zod`'s `ResponseSerializationError` — every test fixture in the audit-log work had been hand-authored fresh, always already carrying the new fields, so nothing caught this until a real project directory with genuine history was loaded in a browser. Fixed by normalizing a legacy entry's missing hash fields to `'legacy'` in `readAuditLog` before it reaches the response schema; `verifyAuditLog` itself needed no change, since it already read the raw file directly and correctly treated a missing hash as unverifiable rather than tampered.
- `apps/studio-web` gains `api/auth-token.ts` (`initStudioToken`/`getStoredStudioToken`); `client.ts`'s `getJson`/`postJson`/`putJson` attach the header when a token is present and produce a distinguishable, actionable error message on a 401 specifically.
- `packages/studio-core`'s and `packages/studio-design`'s `http-contracts.ts` gain `.max()` bounds on every previously-unbounded string/array request field (see Decision above); `app.ts` makes the `1_048_576`-byte body limit explicit.
- `packages/studio-core`'s `AuditEntry`/`AuditListResponse` gain `previousEntryHash`/`entryHash`/`verification`, all required and exposed on the public HTTP response, not internal-only — the hash must be persisted to disk regardless, so hiding it from the response while it's in plain sight in the `.jsonl` file would be an inconsistency for no security benefit, matching how `.afplan`'s `contentHash` and `TestResultsRecord`'s equivalent are both ordinary serialized fields, never treated as secret.

## Security impact

Every new control here is additive and opt-in; a Studio instance with neither `AGENTFORM_STUDIO_TOKEN` nor a rate limit configured behaves exactly as it did before this ADR. This is deliberately _not_ a full multi-tenant auth system — no user accounts, no per-user permissions, no session expiry — the same narrower scope ADR-0016 already chose for Studio as a whole, applied consistently to this specific mechanism. The audit hash chain is detection, not prevention: it makes tampering with `.agentform/studio-audit.jsonl` after the fact visible, the same honest limit `.afplan` has always had, not a guarantee that the file can't be edited directly.

## Migration impact

Fully additive. A project or developer setup with neither `AGENTFORM_STUDIO_TOKEN` nor `AGENTFORM_STUDIO_PORT`/`AGENTFORM_STUDIO_GENAI_PROVIDER` set behaves identically to before this ADR — zero-config Studio usage is unaffected. The one behavior change with no opt-out is the fail-loud config validation: a deployment that was previously (silently, incorrectly) relying on an unrecognized `AGENTFORM_STUDIO_GENAI_PROVIDER` value quietly falling back to `'anthropic'`, or an out-of-range `AGENTFORM_STUDIO_PORT` being coerced into _something_, will now see a startup crash with a readable `StudioConfigError` message instead — a deliberate, confirmed decision (see Consequences above), not an oversight.
