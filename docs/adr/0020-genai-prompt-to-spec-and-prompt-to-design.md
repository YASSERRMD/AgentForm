# ADR-0020: GenAI prompt-to-spec and prompt-to-design

## Status

Accepted

## Context

Phase 17 delivers §34.3's own scope: "GenAI integration: prompt-to-spec (new resources), prompt-to-design (layout suggestions). Provider-neutral (interface + adapters). Every generated artifact passes through the same validate → IR → policy pipeline before acceptance." The frontend never talks to a model provider directly — `apps/studio-web` never imports `packages/studio-genai`, not even for types.

Two things were verified directly against real installed code before designing anything, not assumed:

1. **How does the Anthropic SDK actually do structured output?** `@anthropic-ai/sdk` was installed fresh (`pnpm add`, letting it resolve the real latest version — an earlier guess at a version number was deliberately thrown away rather than kept) and its `.d.ts` files read directly. `client.messages.parse({..., output_config: {format: zodOutputFormat(schema)}})` returns `message.parsed_output: T | null`, already Zod-validated — no hand-rolled JSON parsing or tool-use-forcing needed anywhere in this package.
2. **Does the Anthropic SDK's client throw at construction time with no API key present?** Read `client.mjs` directly: `new Anthropic({apiKey: undefined})` with no `ANTHROPIC_API_KEY` in the environment sets `this.apiKey = null` and defers any auth failure to the first real request. This is what makes `AGENTFORM_STUDIO_GENAI_PROVIDER=anthropic` (the default) safe to construct unconditionally at server startup — a missing key surfaces as a clean, catchable error at generate-time, never a boot crash.

## Decision

- **`packages/studio-genai` is a new, seventh Studio package, with a single entry point and no browser-safe split at all** — unlike `studio-core`/`studio-design`, it needs none, because `apps/studio-web` never imports it. `GenAIProvider` (`{name, generate<T>(request): Promise<T>}`) is the whole provider-neutral surface; `GenAIRequest<T>` carries a real Zod schema per call, handed straight to whichever provider implements it.
- **`FakeProvider` and `AnthropicProvider` are the two implementations, with clearly different jobs.** `FakeProvider` scripts exact responses in order and throws once exhausted — correct for tests, which know exactly how many calls happen. `AnthropicProvider` uses the real `messages.parse`/`zodOutputFormat` mechanism above; it is never live-tested with a real key during this build (the same "no key, no real provider call" discipline this project has followed since the framework adapters' own real-provider testing) — live verification is an explicit, separate, user-initiated step.
- **`promptToSpec` and `promptToDesign` are pure orchestration — they never validate or write anything themselves.** Each calls its provider and reshapes the result; the caller runs the output through the real validation pipeline before it can ever be shown as accepted. This is enforced structurally, not just by convention: neither function imports anything from `@agentform/parser`, `@agentform/ir`, or `@agentform/policy` beyond what's needed to shape a request/response.
- **`generatedSpecProposalSchema` reuses the real `modelSchema`/`toolSchema`/`agentSchema`/`workflowSchema` from `@agentform/schema` directly**, not hand-authored approximations — handed straight to the provider's structured-output mechanism, so a generated resource is schema-conformant the moment `provider.generate` resolves. Likewise `promptToDesign` reuses the real `formLayoutSchema` from `@agentform/studio-design`.
- **Prompt-to-spec is add-only: a proposed resource id that already exists is excluded from the patch and reported in a separate `skipped` array with a reason**, never silently overwriting hand-authored content. Prompt-to-design is scoped to one agent's form layout only, never workflow canvas positions — dagre's deterministic auto-layout already produces good positions for free, and there is no real basis for an LLM to usefully guess x/y coordinates, whereas grouping/ordering named form fields is a genuinely LLM-suited task.
- **`apply-spec-patch.ts`'s validation pipeline is split into a new, non-writing `validateSpecPatch`** (discoverEntryFile → loadProject → multi-file check → applyPatch → buildSpecDocument → loadPolicyConfig → evaluatePolicies), which `applySpecPatch` now calls before its own write step. This is what lets `POST /api/genai/prompt-to-spec` preview a proposal through the _exact_ pipeline `POST /api/spec/patch` will run again on accept — a preview that approves something the write path then refuses (or vice versa) would be worse than not previewing at all. No analogous extraction was needed on the design side: `validateDesignArtifact` (Phase 16) was already a pure, standalone function with no I/O, so the GenAI design-preview route reuses it directly, the same way `applyDesignPatch` already does.
- **Both GenAI endpoints are preview-only and never write.** `POST /api/genai/prompt-to-spec` returns `{success, summary, patch, skipped, diagnostics}`; `POST /api/genai/prompt-to-design` returns `{success, design, diagnostics}` (a fully stamped, validated `DesignArtifact` preview). Accepting a proposal means re-submitting to the real write endpoints (`POST /api/spec/patch`, `PUT /api/design/:resourceType/:resourceId`), which re-validate from scratch rather than trusting that the preview call is still fresh.
- **Provider selection is env-driven (`AGENTFORM_STUDIO_GENAI_PROVIDER`), defaulting to `'anthropic'`**, not a key-free stand-in — it's the only provider that does real work, and constructing it is always safe (see Context). A missing key fails cleanly and catchably the moment GenAI is actually used, matching how every other "you need to configure X" moment in this project's own tooling already behaves. `AGENTFORM_STUDIO_GENAI_PROVIDER=local-demo` selects a **new, third provider implementation** (`lib/local-demo-provider.ts`, studio-server-only — not part of `packages/studio-genai`'s public two): for any schema it's asked to satisfy, it returns the first of a short list of generic "nothing to propose" shapes that happens to validate, so the real orchestration and validation pipeline still runs end to end with no network call and no key. It never pretends to have generated anything — its one meaningful output field says so explicitly. This exists for trying the UI, and was used for this phase's own real-browser verification (see Consequences).
- **HTTP contracts stay co-located with the domain type they carry, not centralized in `studio-core`.** `PromptToSpecRequest`/`Response` live in `studio-core` next to `SpecPatch`; `PromptToDesignRequest`/`Response` live in `studio-design` next to `DesignArtifact` — matching how the Phase 16 design contracts already live in `studio-design`, not `studio-core`. `studio-core` cannot depend on `studio-genai` (the dependency already runs the other way), so `PromptToSpecResponse.skipped` mirrors `studio-genai`'s `SkippedResource` shape structurally rather than importing it — the same deliberate self-contained-mirror choice `studio-design`'s `http-contracts.ts` already makes for `Diagnostic`.
- **The UI reuses the real write paths for acceptance, never a special GenAI-only write.** `GenerateSpecPanel` (new, top-level in `App.tsx`) re-submits an accepted patch to the existing `patchSpec` API call — the same one `ResourceEditor`'s Save button uses. The `FormLayoutEditor`'s new "Generate layout with AI" panel loads an accepted proposal into the editor's own draft state (the same state its up/down/add-field controls already mutate) rather than calling `putDesign` itself — the existing "Save layout" button is still the only thing that persists anything, so an accepted proposal can still be hand-tweaked before it's ever written. Both panels disable Accept whenever the preview's own `success` is false.

## Alternatives considered

- **Manual JSON parsing or tool-use-forcing for structured output**: the default assumption before checking the installed SDK. Rejected once `messages.parse`/`zodOutputFormat` were confirmed to exist and do exactly this, directly against real Zod schemas — eliminates an entire class of hand-rolled-parsing bugs for zero extra code.
- **Making `FakeProvider` itself the server's key-free default**: considered, since it already exists and is well-tested. Rejected because its "throw once scripted responses are exhausted" contract is correct for tests (which know the exact call count) and wrong for a long-running server handling arbitrary, unbounded requests — it would fail every request past however many were pre-scripted. Built `local-demo` as its own small, honestly-labeled implementation instead.
- **Defaulting `AGENTFORM_STUDIO_GENAI_PROVIDER` to the key-free provider**: considered, reasoning that a fresh `agentform studio` install should "just work." Rejected as actively misleading — there is no free inference to default to, and every comparable AI-integrated dev tool requires an explicit key rather than silently degrading to a non-functional stub. `'anthropic'` stays the default; `local-demo` is an explicit, documented opt-in.
- **Centralizing all GenAI HTTP DTOs in `studio-core`**: considered for consistency with `SpecDocumentResponse`/`PatchSpecResponse`/etc. Rejected in favor of the established co-location-by-domain-type pattern once it became clear `PromptToDesignResponse` needs `DesignArtifact`, which `studio-core` does not (and, to avoid a circular dependency, must not) depend on.
- **Skipping the `validateSpecPatch` extraction and duplicating the pipeline in the GenAI route**: considered as the smaller diff. Rejected because it creates exactly the kind of two-copies-that-can-drift risk this whole design is built to avoid — a duplicated pipeline is one refactor away from a preview/write mismatch that would silently undermine "every generated artifact passes through the same pipeline."

## Consequences

- New package `packages/studio-genai`, server-side only, depending on `@agentform/schema`, `@agentform/studio-core`, `@agentform/studio-design`, and `@anthropic-ai/sdk`.
- `apps/studio-server` gains a new non-writing helper (`lib/validate-spec-patch.ts`), a new diagnostic code (`GENAI_GENERATION_FAILED`, `AGF8006`, continuing the reserved `AGF8xxx` Studio range), a provider-resolution layer (`lib/genai-provider.ts`, `lib/local-demo-provider.ts`), and two new routes (`POST /api/genai/prompt-to-spec`, `POST /api/genai/prompt-to-design`).
- `apps/studio-web` gains a top-level "Generate with AI" panel and a per-agent "Generate layout with AI" panel; `api/client.ts` gains `promptToSpec`/`promptToDesign`, both following the established "`success: false` is a real outcome, not an HTTP error" contract.
- Verified end-to-end in a real browser against a real running `studio-server` (`AGENTFORM_STUDIO_GENAI_PROVIDER=local-demo`, no real API key in this session): both endpoints round-trip correctly, Accept is disabled exactly when the preview reports failure or nothing to apply, and accepting a design proposal updates the draft without ever calling the real write endpoint — confirming the preview/accept separation holds in practice, not just in unit tests.
- Found and fixed, as a side effect of this phase's own verification: `apps/studio-web`'s vitest config had no `exclude` for its own `dist/` build output, so every test there was silently running twice (once from source, once from a stale or freshly-recompiled copy in `dist/`) since Phase 13, and could fail outright when an incremental `tsc -b` build left `dist/` internally inconsistent. Fixed with an explicit `exclude: [...configDefaults.exclude, '**/dist/**']`.

## Security impact

Two new write-adjacent endpoints that never actually write: both GenAI routes are preview-only, and acceptance is always a fresh call to an existing, already-hardened write endpoint that re-validates from scratch. No new secret-handling surface — the Anthropic API key is read only by the SDK's own `process.env['ANTHROPIC_API_KEY']` fallback, never touched, logged, or forwarded by any code in this repo. Generated spec proposals pass through the same AF001 secret-detection policy as any hand-authored patch, since they go through the identical `validateSpecPatch` pipeline. A prompt is user-authored, local input to a local server — the only network call this feature ever makes is the outbound request to the configured model provider.

## Migration impact

Additive. A project with no `ANTHROPIC_API_KEY` and no `AGENTFORM_STUDIO_GENAI_PROVIDER` set behaves exactly as before this phase for every existing endpoint; the two new GenAI routes exist and respond, but any attempt to generate fails cleanly with a diagnostic explaining why. Nothing here changes the patch wire format, the design artifact format, or any other resource type's editing experience.
