# ADR-0018: Canvas workflow graph editor

## Status

Accepted

## Context

Phase 15 turns `workflows` from Phase 14's raw-JSON `ResourceForm` fallback (its `nodes`/`edges` shape doesn't fit ResourceForm's flat-object/enum/nested-fixed-object cases) into a real, purpose-built visual editor: a node/edge canvas backed by the same `agentform.yaml` spec everything else in Studio reads and writes, with live graph validation and a risk warning on edits that remove a safety gate.

Before any design decision, two things were verified empirically rather than assumed:

1. **What does the IR actually add to a workflow's nodes/edges?** Researched directly: `IRWorkflowNode`/`IRWorkflowEdge` are literal type aliases of the schema's `WorkflowNode`/`WorkflowEdge` (`packages/ir/src/types.ts`), and `buildIR` performs zero content transformation on them — only `Record → Map` re-keying and an `edges ?? []` default (`packages/ir/src/build.ts`). The already-JSON-safe `AgenticApplication` `GET /api/spec` already returns today contains 100% of the node/edge content a canvas needs.
2. **Can `@agentform/ir` be imported into the browser for real, in-process validation?** `buildIR`/`computeContentHash` transitively import `node:crypto` (`packages/ir/src/hash.ts`). A production `vite build` tree-shakes that dead code out cleanly (verified: zero `node:crypto`/`createHash` in the built bundle), but Vite's dev server evaluates each ES module eagerly and throws the moment `hash.ts` loads — verified with a real spike build and a real `pnpm dev` run before committing to the design.

## Decision

- **Canvas rendering: `@xyflow/react` (React Flow) + `@dagrejs/dagre` for auto-layout.** Mature, MIT-licensed, purpose-built for node/edge diagrams — matches this repo's demonstrated bias toward established ecosystem tooling (ADR-0016's Vite/Fastify reasoning) over hand-rolled SVG canvas code. Real API verified against the installed packages' own `.d.ts` files before use, not assumed from training data (`Node<Data,Type>`, `NodeProps<T>`, `useNodesState`/`useEdgesState`, dagre's `graphlib.Graph`/`layout`/`node()`).
- **No position persistence in Phase 15.** Neither the IR nor the CLI's mermaid/DOT/JSON graph renderers (`apps/cli/src/lib/graph-render.ts`) compute or store node positions — layout has always been presentation, not spec content. The canvas auto-lays-out via dagre on every structural change and never writes x/y anywhere; a real, persisted layout artifact (`.afdesign.json`, `packages/studio-design`) is explicitly Phase 16's concern, recorded here as a deliberate deferral, not a silent gap.
- **No new HTTP endpoint, no IR exposure over the wire.** `buildSpecDocument` keeps discarding the Map-keyed IR exactly as it has since Phase 13 (ADR-0016) — the existing `GET /api/spec` response is sufficient, per the verification above.
- **Live validation reuses the real, unforked validator via a new `@agentform/ir/browser` subpath export**, not a client-side reimplementation. `packages/ir/src/browser.ts` re-exports only `validateSemantics` and its dependencies (`references.ts`, `graph.ts`, `subworkflow.ts`, `permissions.ts`, `outputs.ts`, `limits.ts` — confirmed to have zero transitive dependency on `hash.ts`/`build.ts`), with a new `"./browser"` entry in `package.json`'s `exports` map. This is purely additive to the existing full barrel (`.`), used unchanged by the CLI/compiler/`studio-server`. The canvas calls it (debounced, 300ms) against a draft `AgenticApplication` with the in-progress workflow substituted in, rendering the exact same diagnostics a real `agentform validate`/the server's patch endpoint would — not an approximation.
- **The patch strategy needed zero new machinery.** `workflows` is already one of the four resource types `ResourceEditor` sends as a single whole-resource `add`/`replace` patch (ADR-0017). `WorkflowCanvas` is a drop-in replacement for `ResourceForm` in that same slot — it takes `(value, onChange)` and lets `ResourceEditor`'s existing save/cancel/diagnostics flow own the actual `patchSpec` call, unchanged. No node-path or edge-array patch primitives were added; `applyPatch`'s generic, arbitrary-depth path engine (already generic since ADR-0017) was never touched.
- **Risk signaling is a new, narrowly-scoped, purely structural check — not a reuse of `@agentform/planner`'s `classifyRisk`/`PlanRisk`.** Traced `classifyRisk` directly: it diffs a resource's `CREATE`/`UPDATE`/`REPLACE`/`DELETE` operation against previously-_deployed_ `ResourceState`, a concept Studio's architecture has never loaded and doesn't have access to here (Studio only ever reads/writes the source spec). Reusing that vocabulary for an unsaved local canvas edit would conflate two different questions. Instead, `packages/studio-core/src/workflow-risk.ts`'s `findUngatedDestructiveToolNodes` ports the exact same structural signal `@agentform/policy`'s `AF004` already enforces server-side (a `destructive`-sideEffect tool node with no incoming edge from a `humanApproval` node) to run against one in-memory draft workflow — an earlier, optimistic echo of AF004, which remains the sole real enforcement (already running on every `POST /api/spec/patch` call since Phase 14, unchanged).
- **One parameterized node component, not 13.** All 13 real node types (`agent`, `tool`, `router`, `parallel`, `join`, `loop`, `humanApproval`, `delay`, `event`, `subworkflow`, `transform`, `condition`, `terminate` — verified against the real `workflowNodeSchema` discriminated union) share the same visual structure (a colored category bar, id, type, one-line summary of the type's own distinguishing field) and only the content differs; `WorkflowNodeShape` is data-driven off `workflow-node-visuals.ts`'s category/color/summary lookup instead of 13 near-duplicate files.
- **Node editing reuses the exact variant-picker-then-`ResourceForm` pattern `ResourceEditor` already established for `tools`' discriminated union — applied one level deeper.** `generateWorkflowNodeFormSchema()` (`packages/studio-core/src/form-schema.ts`) generates a real JSON Schema for `workflowNodeSchema` itself (a 13-way `oneOf`, the same shape `z.toJSONSchema` already produces for `tools`' union). `WorkflowNodeEditor` resolves which of the 13 shapes it's editing via the same discriminator-picker logic, then hands one concrete schema to the unmodified `ResourceForm`. `isRecord`/`discriminatorConst` — previously private to `ResourceEditor.tsx` — moved to a shared `lib/json-schema-utils.ts` so this second real consumer doesn't duplicate them.
- **Mutation logic lives in pure functions (`lib/workflow-edit-ops.ts`), not inline in the component.** `addNode`/`updateNode`/`deleteNode`/`setEntrypoint`/`addWorkflowEdge`/`deleteEdge`/`updateEdgeWhen` are plain `(Workflow, ...) => Workflow` functions, unit-tested directly. This was a deliberate architecture choice made once React Flow's real DOM/SVG interaction model (drag-to-connect handles, `getBoundingClientRect`-based hit testing) proved impractical to simulate reliably in jsdom — the _editing behavior_ is fully tested without needing to fake canvas drag gestures; `WorkflowCanvas.test.tsx` still exercises the real, unmocked component end to end for everything that _is_ reliably clickable in jsdom (node click, form submission, button clicks).
- **Deleting the entrypoint node is refused via a disabled button, not a silent no-op or a client-side guess at a replacement.** The user must explicitly pick a new entrypoint first.

## Alternatives considered

- **Persisting canvas positions in the spec itself**: rejected — position is presentation, not application behavior; the spec staying purely behavioral is a core, repeatedly-reinforced principle across every prior Studio ADR. A dedicated design-artifact file is the right home, and that's explicitly Phase 16.
- **Exposing the Map-keyed IR over a new HTTP endpoint**: considered, then rejected after verifying the IR adds zero content to workflow nodes/edges beyond `Map` convenience — building the endpoint would be real, unjustified complexity for data the client already has.
- **Reimplementing a subset of graph validation client-side**: rejected outright — this project's standing discipline (ADR-0016/0017) is to reuse the real validator verbatim, never fork logic that can drift from the server's actual behavior. The `@agentform/ir/browser` subpath was built specifically so this reuse was possible without a Node-only runtime dependency leaking into the bundle.
- **A field-level or node-level patch primitive for canvas edits**: considered (to avoid sending a whole workflow on every keystroke), then rejected — `WorkflowCanvas` batches all edits into one local draft and sends a single patch only on explicit Save, exactly like every other resource type already does; no new patch granularity was needed.
- **Reusing `@agentform/planner`'s `classifyRisk` directly**: rejected after tracing its actual implementation — it's fundamentally a deploy-time, state-diffing concept that doesn't apply to an unsaved canvas edit; force-fitting it would have been a misleading abstraction, not a real simplification.

## Consequences

- `packages/ir` gains its first subpath export (`./browser`) and its first file with an explicit "browser-safe" contract (`browser.ts`), guarded by a regression test that statically checks it never imports `hash.js`/`build.js`/the full barrel.
- `packages/studio-core` gains `workflow-risk.ts` and `generateWorkflowNodeFormSchema`, and its `types.ts`/`index.ts` re-export boundary extends to `Tool`/`Workflow`/`WorkflowEdge`/`WorkflowNode`/`WorkflowNodeType` from `@agentform/schema`, so `apps/studio-web` continues to never import `@agentform/schema` directly (the rule ADR-0016 established for `AgenticApplication`/`Diagnostic`).
- `apps/studio-web` gains its first two new runtime dependencies (`@xyflow/react`, `@dagrejs/dagre`) and a workspace dependency on `@agentform/ir` (via the `/browser` subpath only). `ResourceEditor` gains a new required `application` prop, read only when editing a `workflows` resource.
- Two real, non-obvious bugs were found and fixed during this phase, not just designed around: `@dagrejs/dagre`'s `Graph#setNode` stores the label object by reference and `dagre.layout()` mutates it in place — passing the same box object for multiple same-sized nodes silently collided their reported positions (`layoutWorkflowNodes` now defensively clones); and mixing the `border` shorthand with a `borderLeft` longhand in the same React style object triggers a real React warning about style-diffing bugs across re-renders (`WorkflowNodeShape` now uses explicit `borderTop`/`Right`/`Bottom` throughout).
- `setup-tests.ts` gains a minimal `ResizeObserver` stub — `@xyflow/react` measures its container on mount, which jsdom doesn't implement; this is now available to every test in the package, not just the canvas's own.

### A real bug the `@agentform/ir/browser` split alone didn't catch — found only by real browser verification

Unit tests and a static "does `browser.ts` import the forbidden files" regression guard all passed, but the real `pnpm dev` browser session (per this repo's own "verify UI changes in a real browser" standing rule) still rendered a blank page. Root cause, traced empirically rather than guessed: `apps/studio-web` had _always_ imported types from `@agentform/studio-core`'s main barrel since Phase 13, but only as `import type` — erased entirely at build time, so the barrel's actual JS was never evaluated in the browser. Phase 15 is the first time `apps/studio-web` imports a real _value_ from that barrel (`findUngatedDestructiveToolNodes`, `generateWorkflowNodeFormSchema`), which for the first time forced the browser to evaluate `@agentform/studio-core/dist/index.js` — which re-exported `buildSpecDocument` (`spec-document.ts`), which imports `@agentform/ir`'s **full** barrel (`buildIR`), which imports `hash.ts` (`node:crypto`). The `@agentform/ir/browser` subpath didn't help here because the crash wasn't in code `apps/studio-web` imported from `@agentform/ir` directly — it was in an unrelated import several layers away in a package `studio-web` already depended on for something else entirely.

Fixed the same way, one layer further out: `buildSpecDocument` moved out of `@agentform/studio-core`'s main barrel into a new `@agentform/studio-core/server` subpath (the only consumer, `apps/studio-server`, updated to import from there); the main barrel is now genuinely free of any transitive `@agentform/ir` reference.

Re-testing in the browser _then_ surfaced a second, independent instance of the identical class of bug: `packages/ir/src/semantic/graph.ts` — itself part of `@agentform/ir/browser`'s own dependency tree — imported `findCycle`/`reachableNodes`/`sinkNodes` from `@agentform/core`'s **main** barrel, which also re-exports `walkSourceFiles` (`node:fs`) and `resolvePathWithinRoot` (`node:path`). `packages/ir/src/semantic/subworkflow.ts` had the same problem for `findCycle`. Fixed with the identical pattern one package lower in the dependency chain: a new `@agentform/core/browser` subpath re-exporting only the pure, dependency-free pieces (`duration.ts`, `flatten-maps.ts`, `slugify.ts`, `graph.ts`); both `semantic/graph.ts` and `semantic/subworkflow.ts` now import from it instead of the main barrel.

The general lesson, recorded here because it will recur: a "does this one entry file's own imports avoid the forbidden files" regression test is necessary but not sufficient — it only checks direct imports, not the transitive closure. The `browser.test.ts` regression guards in both `packages/core` and `packages/ir` were rewritten to check every file in the actual dependency tree individually, not just the public entry point, specifically because checking only the entry point is exactly what let the `semantic/graph.ts` instance of this bug slip through a first round of "fixed and tested" review. No amount of unit or component testing (all of which mock `@agentform/ir/browser`'s call sites or never exercise the real module graph) would have caught any of this — only an actual browser, loading actual unbundled ES modules through Vite's dev server, surfaced it. This is the concrete justification for why this repo's "start the dev server and use the feature in a browser before reporting the task as complete" rule exists, not a formality.

## Security impact

No new write surface: canvas edits flow through the identical `POST /api/spec/patch` path (ADR-0017) that already re-validates unconditionally server-side — the client-side live validation and risk warning are optimistic UX, never a new authority. No new secret-handling surface. The one new client-side dependency on `@agentform/ir` was scoped specifically (via the `/browser` subpath) to avoid pulling any Node-only API into the browser bundle; verified empirically that the production bundle contains zero `node:crypto`/`node:fs`/`node:path` references despite Vite's resolver visiting those modules during dependency analysis.

## Migration impact

Additive to Studio. `workflows` resources are now edited via the canvas instead of `ResourceForm`'s raw-JSON fallback; no change to any other resource type's editing experience, to the patch wire format, or to any CLI command's behavior.
