# ADR-0021: Edit-by-chat and unified proposal pipeline

## Status

Accepted

## Context

Phase 18 delivers §34's closing scope for the Agentform Studio arc: "Conversational edits to spec and design -> diffs through the full pipeline. Unified accept/reject flow with plan + risk + policy shown together. Provenance and audit on every applied change." This is the sixth and final phase of the arc that began with ADR-0016 (Studio foundation) — this ADR closes it.

Phase 17 (ADR-0020) already built one-shot GenAI generation with a real, tested preview → accept → re-validate pipeline. Phase 18's job is not a new pipeline but two extensions to it: making a proposal _conversational_ (multi-turn, can reference and edit what already exists, not just propose new resources) and making every applied change _provenanced_ (who/what proposed it, visible after the fact).

## Decision

- **Chat's proposal output is a real `SpecPatch` directly (`{op: 'add'|'replace'|'remove', path, value}`), not Phase 17's add-only, resource-bucketed shape.** This is the concrete mechanism behind "conversational edits" being edits and not just conversational generation: a chat turn can `replace` an existing agent's `role` or `remove` a stale workflow, which Phase 17's shape structurally cannot express. `chatSpecResponseSchema`/`chatDesignResponseSchema` (new, in `packages/studio-genai`) are each a discriminated union on `type`: `'message'` (a plain reply, `{type, message}`) or `'proposal'` (`{type, message, patch}` / `{type, message, layout}`). Every safety property from Phase 17 carries over unchanged: still preview-only, still validated through the exact same `validateSpecPatch`/`validateDesignArtifact` pipeline before `success` can be `true`, still requires re-submission to the real write endpoints to persist anything.
- **`GenAIProvider`'s request gains an optional `history?: readonly GenAIHistoryMessage[]`**, non-breaking (`FakeProvider` needs no change since it already records the whole request; `AnthropicProvider` threads it into the real SDK `messages` array ahead of the new user turn). This is the entire mechanism multi-turn conversation rests on — no session state on the server at all; the client resends the full transcript every turn, the same stateless-request discipline every other Studio endpoint already follows.
- **A local, append-only provenance log (`.agentform/studio-audit.jsonl`), explicitly not a security control.** Every successful write (`applySpecPatch`, `applyDesignPatch`) appends a stamped `AuditEntry {timestamp, source, summary, target}` after its own write succeeds. `source` is `'manual' | 'genai' | 'chat'`, carried as an optional `ChangeProvenance` on `PatchSpecRequest`/`PutDesignRequest` (defaults to `'manual'` server-side, so every pre-Phase-18 caller needs no change). Deliberately unlike `@agentform/planner`'s hash-verified, tamper-evident `.afplan` files — this is local operational visibility ("what changed and where did it come from"), nothing more. Lives under `.agentform/`, matching the CLI's own local/uncommitted-by-convention state directory, not `design/` (shared, meant to be committed).
- **`POST /api/genai/chat/spec` and `/chat/design` mirror `routes/genai.ts`'s established shape**, branching on whether the orchestration function returned a proposal or a plain reply: a plain reply short-circuits to `{success: true, message, diagnostics: []}` with nothing to validate; a proposal runs through the identical validation pipeline the one-shot endpoints and the real write endpoints all share.
- **A new, unified `ProposalReview` component replaces the duplicated proposal-review JSX** that had independently grown inside Phase 17's `GenerateSpecPanel` and `GenerateLayoutPanel` (summary, changes list, skipped resources, diagnostics, accept/reject — copy-pasted with small drifts between the two). Every proposal source in Studio — chat and, retroactively, anything upstream — now renders through one component, taking a generic `{summary?, changes?, skipped?, impact?, diagnostics, canAccept, acceptBusy, onAccept, onReject}` shape rather than a specific response type, so it composes with both `ChatSpecResponse`/`ChatDesignResponse` today and whatever shape a future proposal source might carry.
- **A new risk/impact signal, `classifyPatchImpact` (`packages/studio-core`), deliberately distinct from `@agentform/planner`'s `classifyRisk`/`PlanRisk`.** Planner's classification is relative to previously-_deployed_ state (via `@agentform/state`), which Studio has no access to — the same distinction `workflow-risk.ts`'s `findUngatedDestructiveToolNodes` already drew in Phase 15. Approximating planner's real classification here, without real deployed state to compare against, risks disagreeing with what `agentform plan` would actually say once state is involved — worse than a narrower, honest signal. `classifyPatchImpact` answers two questions available from the patch and the document it would apply to, nothing more: does the diff remove or redefine something that already exists (`remove` > `replace` > purely additive), and — reusing `findUngatedDestructiveToolNodes` exactly as `WorkflowCanvas` already does, via `applyPatch(currentApplication, patch)` — would the resulting spec contain an ungated destructive tool call. Design/layout proposals carry no impact signal at all: a layout is presentation-only and never touches `spec.*` behavior, so the question doesn't apply to it.
- **Chat replaces Phase 17's one-shot panels rather than running alongside them.** `GenerateSpecPanel` and `GenerateLayoutPanel` are deleted; `ChatSpecPanel` and `ChatDesignPanel` take their place in `App.tsx` and `FormLayoutEditor.tsx` respectively. A fresh conversation's first message covers the exact one-shot use case the old panels served — chat is a strict capability superset, not a parallel feature — and keeping both would have meant two overlapping, redundant "propose via AI" entry points on the same page. The Phase 17 one-shot HTTP endpoints (`POST /api/genai/prompt-to-spec`/`/prompt-to-design`) and their orchestration functions are untouched and still real, tested, documented API surface — only the studio-web UI and its now-unused `promptToSpec`/`promptToDesign` client wrappers are removed, since nothing in studio-web calls them anymore.
- **A small `AuditPanel` in `App.tsx`** lists recent entries from `GET /api/audit` (timestamp, source, target, summary), newest first. Manual refresh rather than auto-refresh on every mutation: design saves (`FormLayoutEditor`) don't share `App`'s own `load()` reload cadence, and wiring a cross-panel "something changed" event for a small recent-changes list isn't proportionate to what it buys.

## Alternatives considered

- **Keeping chat's proposal shape add-only, matching Phase 17**: considered, since it would have reused `generatedSpecProposalSchema` unchanged. Rejected because it would make "conversational edits" a misnomer — an add-only shape cannot express "change this agent's role" or "remove that workflow," the exact cases a multi-turn edit conversation exists for.
- **Server-side conversation state, addressed by a session id**: considered as the more familiar chat-app pattern. Rejected in favor of the client resending the full transcript every turn — no new server-side state store, no session lifecycle/expiry to design, and it matches every other Studio endpoint's already-stateless request/response contract.
- **Reusing `@agentform/planner`'s `classifyRisk` for the proposal review's risk signal**: considered directly, since it's the project's one real, authoritative risk classification. Rejected — see Decision above; it needs `ResourceState` diffing against deployed state and IR-shaped workflow data, neither of which a raw, unapplied `SpecPatch` preview has, and reproducing an approximation risks being actively misleading rather than merely incomplete.
- **Keeping the Phase 17 one-shot panels alongside the new chat panels**: considered as the more conservative, purely-additive option. Rejected as a UX regression, not a safety-preserving choice — two boxes doing overlapping things on the same page is worse than one, and nothing is lost functionally since a fresh chat's first turn already covers the one-shot case.
- **Auto-refreshing `AuditPanel` after every mutation across the app**: considered for a more "live" feel. Rejected as disproportionate plumbing (a new cross-panel event, or threading a refresh callback through every panel that can produce a write) for what a manual Refresh button already delivers honestly and simply.

## Consequences

- New exports from `packages/studio-genai`: `chatEditSpec`/`chatEditDesign`, `chatSpecResponseSchema`/`chatDesignResponseSchema`, `GenAIHistoryMessage`.
- `packages/studio-core`/`packages/studio-design` each gain `ChangeSource`/`ChangeProvenance`, `ChatHistoryMessage`, `ChatSpecRequest`/`Response` (or `ChatDesignRequest`/`Response`), and `studio-core` gains `AuditTarget`/`AuditEntry`/`AuditListResponse` and `classifyPatchImpact`/`PatchImpactLevel`.
- `apps/studio-server` gains `lib/audit-log.ts` (append/read/describe), two new routes (`POST /api/genai/chat/spec`, `POST /api/genai/chat/design`, `GET /api/audit`), and every successful spec/design write now also appends one audit entry (existing tests asserting an exact write count were updated from 1 to 2 accordingly).
- `apps/studio-web` gains `ChatSpecPanel`, `ChatDesignPanel`, a shared `ChatTranscript`, the unified `ProposalReview`, and `AuditPanel`; loses `GenerateSpecPanel`/`GenerateLayoutPanel` and the `promptToSpec`/`promptToDesign` client functions.
- Found and fixed, as a direct result of this phase's own real-browser verification against `AGENTFORM_STUDIO_GENAI_PROVIDER=local-demo`: (1) both chat panels were rendering a blank assistant turn, with no visible explanation, whenever generation itself failed (`success: false` with no patch/design) — fixed by treating that case as a turn-level error rather than a reply to add to the transcript; (2) `local-demo-provider`'s fallback candidates (built for Phase 17's two one-shot schemas) satisfied neither chat schema, so every chat message failed outright on a fresh install with no API key — fixed by adding a `{type: 'message', message: NOTHING_GENERATED_MESSAGE}` candidate, which the same honest "never pretends to have generated anything" provider now also satisfies for both chat endpoints.
- Verified end-to-end in a real browser against a real running `studio-server` (`local-demo`, no real API key in this session): a spec chat message, a design chat message, and a plain resource Save each round-tripped correctly, and the `Save` produced a real audit entry (`manual · spec · replace spec.models.primary`) that appeared in `AuditPanel` after Refresh.

## Security impact

Two new endpoints that never actually write (same preview-only contract as Phase 17's), plus one new read-only endpoint (`GET /api/audit`) over a local file already scoped under the project's own `.agentform/` directory via the existing `resolvePathWithinRoot` path-safety helper. No new secret-handling surface: the audit log stores only `{timestamp, source, summary, target}` — never patch/design content, never a prompt, never a secret value — and a chat proposal passes through the identical `validateSpecPatch`/`validateDesignArtifact` pipeline (including the AF001 secret-detection policy) as any hand-authored or one-shot-generated patch. `history` is round-tripped verbatim through the request/response cycle and is never persisted server-side.

## Migration impact

Additive, with one UI-surface removal already covered above (the one-shot panels), not a wire-format or API break: `PatchSpecRequest`/`PutDesignRequest`'s new `provenance` field is optional and defaults to `'manual'`, so every pre-Phase-18 caller of `POST /api/spec/patch`/`PUT /api/design/:resourceType/:resourceId` needs no change. A project with no `.agentform/studio-audit.jsonl` yet behaves exactly as `{entries: []}` — an empty log is a normal state, not an error. This closes the Agentform Studio arc (Phases 13-18, ADR-0016 through this ADR).
