# ADR-0019: Form layout editing and the design layer

## Status

Accepted

## Context

Phase 16 delivers §34.8's own scope exactly: "Form-layout editing tied to schema. `packages/studio-design` + `.afdesign.json` artifact model. Design layer strictly presentational; cannot alter logic/permissions." Its four required tests: layout round-trip, design serialization deterministic, dangling binding rejected, design cannot mutate control flow.

Two things were verified empirically before designing anything, not assumed:

1. **What does an agent's `inputSchema`/`outputSchema` actually look like?** Read `packages/schema/src/agent.ts` directly: both fields are `z.record(z.string(), z.unknown()).optional()` — an entirely unenforced `Record<string, unknown>` bag, not a nested JSON-Schema-shaped object Zod validates the internal structure of. A "form layout editor" for these fields is therefore inherently best-effort: it can only extract a field list when the value _happens_ to be authored in `{ type: 'object', properties: {...} }` convention, and must degrade to "nothing to lay out" rather than guess otherwise.
2. **Is `.afdesign.json` position persistence for the Phase 15 workflow canvas actually in scope here, or a separate future concern?** ADR-0018 recorded it twice as an explicit deferral to "Phase 16's `.afdesign.json`, `packages/studio-design`." The mid-session instruction to fold in anything pending from the previous phase made this an explicit inclusion, not a judgment call: the design artifact model built for form-layout is general enough to hold workflow canvas positions too (§34.5's own layer list names both "Form layout layer" and treats canvas position as presentational), so retrofitting `WorkflowCanvas` to use it is in scope for this phase, not a new one.

## Decision

- **`packages/studio-design` is a new, sixth Studio package** (alongside `studio-core`), matching §34.3's architecture diagram exactly rather than folding design concerns into `studio-core`. It owns the artifact model, validation, and render target — never editing UI (that stays in `apps/studio-web`, matching how `workflow-edit-ops.ts` already lives with its own UI rather than in `studio-core`).
- **One `DesignArtifact` shape serves both subject kinds** (`binding.resourceType: 'agents' | 'workflows'`), not two artifact types. An agents-bound design carries `layout: FormLayout` (an `input`/`output` tree of `container`/`field` nodes); a workflows-bound design carries `positions: Record<nodeId, {x,y}>`. `validateDesignArtifact` enforces that a design never carries the other kind's data (`AGF8005`) — a structural guarantee, not just a convention, that reinforces "design cannot mutate control flow" by making it impossible for a workflow's design to even carry form-layout-shaped content in the first place.
- **`specVersionTarget` and `contentHash` are computed server-side only, at write time**, using `@agentform/ir`'s existing `computeContentHash` (the same content-hash algorithm/format already used everywhere else in this codebase — `.afplan` files, IR hashing). The browser never hashes anything: it submits a `DesignDraft` (binding + layout/positions/styleTokens, no version/hash fields at all), and `stampDesignArtifact` (server-only) fills in the rest. This sidesteps a real question — whether `packages/studio-design`'s hashing needs to be isomorphic (Web Crypto, async) to stay browser-safe — by recognizing the browser never needed to hash in the first place; every write goes through the server regardless.
- **The browser/server split is made proactively, not retrofitted after a crash.** `packages/studio-design/src/server.ts` is the only file importing `@agentform/ir`'s main barrel (`node:crypto` via `computeContentHash`); the main `index.ts` barrel (types, `validateDesignArtifact`, `renderDesignToHtml`, Zod contracts) is pure and browser-safe from the start. This applies ADR-0018's own recorded lesson — three separate barrel-mixing bugs, each found only by an actual browser crash during Phase 15 — before `apps/studio-web` ever gets the chance to import this package and hit the same class of bug a fourth time. `index.test.ts` checks every file in the real dependency tree individually (not just `index.ts`'s own imports), the specific gap that let one of Phase 15's three instances slip through a first "fixed" pass.
- **File naming: `design/<resourceType>.<resourceId>.afdesign.json`**, using `studio-core`'s own plural `ResourceType` convention (`agents`, `workflows`) rather than the CLI's singular `inspect` addressing convention (`agent.<id>`) — these are two already-existing, non-identical conventions in this codebase (confirmed by direct comparison, not assumed to be the same), and `studio-design` sits directly next to `studio-core` as a sibling package, so matching its convention keeps the two consistent with each other rather than inventing a third scheme.
- **Form-layout field extraction is top-level `properties` keys only, no nested traversal.** `extractSchemaFields` (`apps/studio-web/src/lib/extract-schema-fields.ts`) reads `schemaValue.properties`'s own keys, in their real JS object insertion order (same ordering guarantee already verified and relied on for `generateResourceFormSchema`'s output). A deliberate, documented scope limit, not a silent gap: real JSON Schema can nest arbitrarily, but nothing in Phase 16's test list requires it, and going further would mean guessing at a convention the schema doesn't actually enforce at any depth.
- **"Adding a field" to a form layout can only place an _existing_ schema key — it never invents one.** Per §34.5: "adding a field proposes a schema change." The layout editor's own draft never touches `agent.inputSchema`/`outputSchema` content; a genuinely new field has to be added to the schema first (through the agent's own `Fields` tab, Phase 14's existing spec-patch pipeline), after which it becomes available to place in `Layout`. This keeps the two pipelines — spec patch vs. design write — completely non-overlapping, which is what makes "design cannot mutate control flow" a structural fact (two disjoint write paths touching two disjoint files) rather than a promise enforced only by convention.
- **Reordering uses up/down controls, not drag-and-drop.** Mirrors ADR-0018's own reasoning for why `workflow-edit-ops.ts` is tested as pure functions rather than simulating React Flow drag gestures in jsdom: an up/down button click is directly, reliably testable in RTL; a synthetic drag-and-drop sequence is not. Grouping (moving a field into a named container) uses a `<select>` picker for the same reason.
- **Workflow canvas position persistence retrofits `WorkflowCanvas.tsx`** (`buildFlowNodes` now accepts `savedPositions`, per-node override over dagre's auto-layout for any node without one) rather than becoming a new, separate concern. `onNodeDragStop` reads positions from the component's own `nodes` state — not the drag callback's own third argument, whose "every node vs. just the dragged selection" semantics aren't pinned down in `@xyflow/react`'s public docs and getting it wrong would silently drop every other node's saved position — and persists via a debounced `PUT`, matching the same `setTimeout`-based debounce pattern already used for live semantic validation in the same file.
- **The HTML render target (`renderDesignToHtml`) is minimal and structural only.** Per §34.6 ("compiled to a render target, initially: preview HTML"): renders the layout tree's containers/fields/widgets as semantic HTML with escaped text, applies `styleTokens` as CSS custom properties. It never renders runtime data (fields render as empty, named inputs) — there is nothing here that could leak a secret, by construction, not by a scan.
- **A freeform, drag-and-drop mockup canvas UI is explicitly deferred past Phase 16.** §34.1 describes "freeform design / mockups" as a third canvas layer, but Phase 16's own phase-breakdown bullets and test list only require the artifact _model_ ("`packages/studio-design` + `.afdesign.json` artifact model") plus form-layout _editing_ — not an interactive freeform UI. The `LayoutNode`/`StyleTokens` model is intentionally general enough (arbitrary container nesting, a style-token palette) that a later phase can build a freeform editor on top of the same artifact type without a rearchitecture; recorded here as a deliberate scope boundary, not a silent gap.

## Alternatives considered

- **Isomorphic (Web Crypto, async) hashing inside `packages/studio-design` itself**: considered, to let the browser compute/verify hashes client-side for live diffing. Rejected once it became clear the browser never actually needs to hash anything — every design write already goes through the server, which can just as easily compute both `specVersionTarget` and `contentHash` there, using the exact same algorithm `@agentform/ir` already uses everywhere else, with zero new isomorphic-crypto surface.
- **Per-field `resourceRef` bindings inside the layout tree** (for a richer "component bound to any spec resource" model): considered per §34.6's literal "Component bindings to spec resources" wording. Scoped down to a single top-level `binding` per artifact — sufficient for both subject kinds this phase actually needs (one agent's form layout, one workflow's canvas positions) and for the required "dangling binding rejected" test; a multi-binding freeform model is exactly the kind of thing the deferred freeform-mockup UI would need, not form-layout or canvas-position persistence.
- **Splitting `subjectType` as its own field, independent of `binding.resourceType`**: rejected as redundant — `binding.resourceType` (`'agents' | 'workflows'`) already disambiguates which shape a design should carry; a second field asserting the same thing could disagree with the first and would need its own consistency check for no real benefit.
- **A separate `design/<resourceType>/<resourceId>.afdesign.json` directory-per-type layout**: considered, rejected as unnecessary nesting for what's currently at most two designs per resource id; the flat `design/<resourceType>.<resourceId>.afdesign.json` naming is unambiguous on its own.

## Consequences

- New package `packages/studio-design`, structured exactly like `studio-core`: a browser-safe main barrel (`.`) and a Node-only `/server` subpath, from day one.
- `apps/studio-server` gains `GET`/`PUT /api/design/:resourceType/:resourceId`, a write path independent of `apply-spec-patch.ts` with its own, narrower validation (referential integrity only, never schema/semantic/IR/policy — a design artifact isn't a spec resource).
- `apps/studio-web` gains a `Fields`/`Layout` toggle on the agent editor and real position persistence on the workflow canvas; `packages/studio-core`'s `types.ts`/`index.ts` re-export boundary extends to `Agent` (same "`apps/studio-web` never imports `@agentform/schema` directly" rule ADR-0016 established).
- `resourceId` route params are constrained to `@agentform/schema`'s own `identifierSchema` before ever reaching a filesystem path — `resolvePathWithinRoot` is the defense-in-depth backstop, not the only gate. A real, empirically-verified traversal test case (`../../../../../../../etc/passwd`) is included specifically because a shallower one — absorbed into the `design/<type>....` path template's own dots — turned out to stay safely within root, which the test suite proves rather than assumes.
- Continues Studio's reserved `AGF8xxx` diagnostic range (`AGF8002`-`AGF8005`), alongside `studio-server`'s existing `AGF8001`.

## Security impact

New write surface (`design/*.afdesign.json`), scoped narrowly: never touches `agentform.yaml` or any spec file, never runs generated code, never accepts anything beyond a `binding`/`layout`/`positions`/`styleTokens` shape validated by both Zod (structural) and `validateDesignArtifact` (referential). The render target renders structure and widget choice only — never runtime values — so there's no path for a design artifact to leak a secret even indirectly. No change to the existing spec-patch write path or its validation.

## Migration impact

Additive. Existing projects with no `design/` directory behave identically to before this phase — `GET` returns `{design: null}`, the canvas falls back to dagre auto-layout exactly as it did in Phase 15, and the agent editor's `Fields` tab is unchanged. Nothing here changes the patch wire format, any CLI command, or any other resource type's editing experience.
